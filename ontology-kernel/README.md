# OSAHR ontology admission profile

## Product decision before implementation

The first user is provisionally the existing Grok Bot component owner, from
`OSAHR_ISSUE_13_PRODUCT_DECISION.md` (a local planning note outside this repository). Their job is to
review an exact proposed component and understand its resulting membership in
the cell. The prior decision records hypotheses and engineering probes, not
validated product-market fit. No paying customer, measured review-time saving,
or repeat use has been established in this investigation.

**Decision: build only a bounded, executable compatibility experiment.** Reuse
OSAHR's existing matcher, DPO transaction engine, and GrokCell assembly rule.
Use RDFLib, pySHACL, and the external W3C PROV-O vocabulary. Do not build another
ontology database, reasoner, scheduler, agent framework, sandbox, or approval
service. A Foundry deployment should use its native Actions and submission
criteria. A successful local experiment cannot establish product-market fit.

The experiment evaluates a proposed admission on a detached ontology snapshot.
Its output is a candidate snapshot and a provenance record. It does not execute
component source code, authenticate a human, admit into the running GrokCell,
or authorize an external action. Those responsibilities already belong to the
owner's runner and host platform. Tests passing only support the tested contract.

The kernel is a **restricted usage profile of existing code**, not a replacement
kernel. The profile resolves the cell and proposal explicitly and binds both
vertices before applying the existing assembly rule. No random waiting time is
introduced for a user-requested action. The existing stochastic runtime remains
available for separately justified stochastic models.

## Commercial falsification

Compare this path with ordinary CI artifacts plus manual approval and, when a
tenant is available, native Foundry Actions. Use two real pending components with
owner-controlled acceptance tests; record review effort, changed decisions,
replay use, and voluntary next use. Retain the OSAHR layer only if its relational
transition evidence changes a decision or removes recurring work that the
baseline does not already handle. Otherwise keep the existing tools and delete
this experimental integration. No new customer segment is inferred from the
availability of the technology.

The first [real maintenance case](cases/admission-replay/README.md) now repairs
GrokCell's admission replay defect using its existing graph and replay engine.
Ordinary regression tests detect the defect. The case changes an existing module;
it is outside this profile's additive admission domain. No extra correctness or
commercial value for the ontology adapter was demonstrated. A negative-control
test also confirms that a preview can bind failing test evidence: only the host's
independent acceptance gate can make the code-admission decision.

## Run locally

From the repository root in PowerShell:

```powershell
& .\ontology-kernel\run.ps1
# Include the timing experiment:
& .\ontology-kernel\run.ps1 -Benchmark
```

The existing repository `.venv` was used. Only its local environment received
RDFLib 7.6.0 and pySHACL 0.31.0 and their dependencies. A fresh environment needs
Python 3.11 or later, `pytest`, and `ontology-kernel/requirements.txt` installed.
The launcher sets import paths for the existing OSAHR and GrokCell source trees
and restores the caller's environment afterward. It generates synthetic records;
it does not run the proposed module. No network is needed for subsequent runs.
The launcher checks both the ontology profile and the real admission-replay
regression before generating its synthetic preview.

Run the existing kernel suite separately:

```powershell
& .\.venv\Scripts\python.exe -m pytest -p no:cacheprovider --basetemp=ontology-kernel/scratch/core-new-run
```

Use a fresh scratch name. Pytest owns its base temporary directory.

- [Research and mathematical derivation](RESEARCH.md): evidence, locality proof,

- [Executable profile](kernel.py): existing GrokCell assembly rule over a two-vertex
  footprint; existing OSAHR executes the transaction.
- [Operational shapes](shapes.ttl): validation delegated to pySHACL.
- [External ontology source](vendor/SOURCE.md): unmodified, hash-pinned W3C PROV-O.
- [Tests](test_profile.py): independent native-SPARQL comparison, full-context
  differential checks, delta replay, malformed input, freshness, and exact-byte checks.
- [Measured benchmark](artifacts/benchmark.json): timings and all seven samples.
- [Candidate snapshot](artifacts/candidate.ttl), [provenance](artifacts/provenance.ttl),
  and [receipt](artifacts/receipt.json): generated by the runnable synthetic demo.
- [Maintenance case and next decision](cases/admission-replay/README.md): actual
  regression, repair, verification evidence, scope rejection, and conditions for
  proceeding with an owner pilot.

The specialization avoids copying existing members into the temporary DPO graph.
On this machine, with 1,000 existing members, the local rewrite stage took about
0.6 ms versus 33 ms for full-context exhaustive execution. The complete warm
preview still took about 306 ms because RDF validation, copying, and hashing
remain. These are fixture timings, not a production latency guarantee.

## Scope that must remain explicit

This is an executable **preview**, not a deployed Foundry integration. The real
external ontology is PROV-O; the operational data is synthetic. SHACL checks a
small operational profile, not all OWL/PROV semantics. The receipt binds exact
bytes but does not establish evidence truth, authenticated approval, code safety,
or causal effects. Input RDF must remain unchanged for the duration of a call.

The additive membership operation also works with native SPARQL; tests demonstrate
that baseline. OSAHR is justified here only if reusing its existing rule and
transition evidence earns its maintenance cost in actual owner work. Foundry
Actions remain the default for a Foundry customer. The core kernel, frozen
experiments, and live ontologies were unchanged. The follow-up maintenance case
repairs the GrokCell surface's unrecorded membership-cache write; its assembly
rule, schema, and model identity remain unchanged.

Commit-time integration: fast-forwarded to upstream `cdfd4d3`, then verified
173 tests across `tests`, `workbench/tests`, and this profile. A separate
portability commit preserves existing frozen-file bytes on Windows and uses
forward slashes in the upstream benchmark's source manifest. Existing frozen
checksums remain unchanged. Earlier benchmark and verification artifacts retain
their original research-run measurements.
